# Handbook Navigation Model

This document defines how the handbook booklet is navigated. Every navigation device is a deliberate choice — selected because it belongs in a field guide, mapped to a web mechanic that respects the booklet metaphor, and designed so an employee can actually find things.

This is the navigation counterpart to the [design brief](handbook-booklet-experience.md), the [content map](handbook-content-map.md), and the [visual language](handbook-visual-language.md). It answers _how the reader moves_, not _what the pages look like_.

## Navigation Philosophy

A field guide is navigated differently than a website. The governing principles:

**Sequence is the primary axis.** A field guide is arranged with intention — early sections orient, middle sections equip, later sections deepen. The default reading path (page by page, chapter by chapter) is designed to build understanding. This is the opposite of a wiki, where every page is equally accessible from a sidebar and order is arbitrary.

**Landmarks, not menus.** A field guide reader finds their way by recognizing landmarks — chapter openers, running headers, folios, marginalia symbols — not by scanning a persistent navigation tree. The handbook provides these landmarks on every page.

**Pages are discrete units.** Readers advance by page, not by scroll depth. A page is a bounded space with a fixed geometry. Navigation between pages is an explicit action (page turn), not a continuous scroll.

**The TOC is a page, not a component.** In a field guide, the table of contents is a dedicated spread in the front matter — a map of the territory ahead. It is not a collapsible sidebar that follows the reader everywhere. The reader visits it, consults it, and moves on.

**Cross-references are authored, not generated.** Marginalia cross-references ("see page 5") are hand-written pointers placed by an author who knows what the reader might need next. They are not "related pages" generated by a taxonomy engine.

### How This Diverges from Web Conventions

| Web convention | Booklet alternative | Why |
| --- | --- | --- |
| Persistent left sidebar with tree navigation | Table of Contents is its own page in the front matter | A sidebar reads as documentation wiki. A TOC page reads as a book. The reader consults the map, then travels. |
| Top nav bar on every page | Running headers (section left, chapter right) | A nav bar reads as website chrome. Running headers are part of the page — they belong to the booklet, not the browser. |
| Breadcrumb trail (`Home > Section > Page`) | Chapter opener pages + running headers | Breadcrumbs are a web pattern for deep hierarchies. A field guide has shallow structure (chapters → pages) and orients through visual landmarks. |
| Search-as-primary-navigation | Table of Contents + marginalia cross-references + Key to Symbols | Search makes the handbook a database. A field guide rewards knowing the territory. The TOC and cross-references teach the structure; search bypasses it. |
| Infinite scroll or "load more" | Discrete pages with sequential previous/next navigation | Pages are the atomic unit. Turning a page is an intentional act. Scrolling blurs boundaries between sections. |
| Tag/category filtered listing | Chapter structure with authored sequence | Tags are a content-management pattern. A field guide's organization is an authored argument about what matters and in what order. |
| "Related articles" generated links | Authored marginalia cross-references | Machine-generated links are generic. Hand-written marginalia ("If you need the decision-making process, turn to page 15") carry authorial intent. |
| Footer with link farm | Folio (page number) only | A booklet footer is a single number — the reader's location in the sequence. A link farm is web chrome. |

## Navigation Devices

Each device is defined with its booklet form (how it reads as a field guide), its web mechanic (how it is implemented), and its accessibility behavior (how it works for keyboard and screen reader users).

### 1. Cover

**Booklet form:** The handbook's front door. Title, subtitle, edition stamp. No folio (page numbers start after the cover). No running header. The cover is the first thing the reader sees — it establishes the field-guide identity before any content begins.

**Web mechanic:** A dedicated page (`page_form: cover`) at the site root (`_index.md`). The cover is the Hugo home page. No navigation chrome surrounds it — the cover owns the full viewport.

**Accessibility:** The title is an `<h1>`. The subtitle is a `<p>`. The stamp is decorative (no information loss if not perceived). Landmark: the cover `<article>` is the sole content landmark on the page.

**Implementation status:** Implemented (`layouts/partials/booklet/cover.html`).

---

### 2. "How to Use This Field Guide"

**Booklet form:** Front matter, page i. Teaches the reader the handbook's navigation conventions before they start reading — symbols, marginalia, stamps, page numbering, how to navigate. This is the field-guide equivalent of a map legend: _learn to read the guide before you use it._

**Web mechanic:** A dedicated page (`page_form: single-page`) in the front matter. Linked from the cover (or the cover is followed by this page sequentially). No special web mechanics — the page is prose that explains the navigation system to the reader.

**Accessibility:** Standard semantic HTML. The page explains the visual conventions to all readers, including screen reader users who will encounter the same structures (marginalia `<aside>` elements, stamp text, folio numbers) and benefit from knowing what they represent.

**Implementation status:** Defined in content map (page i). Content not yet written.

---

### 3. Table of Contents

**Booklet form:** Front matter, page ii. Lists every chapter with its starting page number and a one-line description. Arranged in reading order. Uses small caps or contrasting type for page numbers. A dotted leader line connects chapter title to page number — the classic book TOC pattern. The TOC is the primary wayfinding device: a reader who wants to jump to a specific topic starts here.

**Web mechanic:** A dedicated page (`page_form: toc`). The TOC is auto-generated from the Hugo section structure, ordered by `page_number` frontmatter. Each entry is an anchor link to the corresponding page. Clicking a chapter title navigates to that page. This is plain HTML — no JavaScript required.

The TOC is reachable from every page via a consistent, booklet-native affordance (see Sequential Navigation below). It is also the natural destination from the cover.

**Accessibility:** The TOC is an `<ol>` with `<a>` links — screen readers announce the list length and navigate by list item. Each link text is the chapter title (not "click here"). Page numbers are in a `<span>` separate from the link, so they are read as supplementary information, not as part of the link text. Focus order follows the reading sequence.

Keyboard: `Tab` through entries, `Enter` to navigate. No focus trap — the TOC is a page, not a modal.

**Implementation status:** Implemented (`layouts/partials/booklet/toc.html`). Currently iterates `.Pages` of the handbook section. Does not yet reflect the full chapter structure from the content map (content reorganization is a separate runtime task).

---

### 4. Running Headers

**Booklet form:** Top of every page (except cover and full-bleed). Left side: section name. Right side: chapter name. Set in small caps, separated by a hairline rule. Like a field guide's running heads, they tell the reader where they are without breaking the page composition.

**Web mechanic:** A `<header>` element within each page `<article>`. The left and right labels are `<span>` elements. Styled with `font-feature-settings: "smcp"` for small caps. No interactivity — running headers are static orientation, not navigation controls.

**Accessibility:** The running header is a `<header>` landmark within the page `<article>`. Screen readers announce it when entering the article. The text is plain content — it orients without requiring interaction.

**Implementation status:** Implemented (`layouts/partials/booklet/running-header.html`). Used by `single-page`, `chapter-opener`, `spread`, `marginalia-heavy`, and `toc` page forms.

---

### 5. Folios (Page Numbers)

**Booklet form:** Bottom outer corner of every page. Format: "— N —" (em-dash, number, em-dash). Left pages: bottom-left. Right pages: bottom-right. Front matter uses lowercase roman numerals (i, ii). Body uses arabic numerals (1, 2, 3…). The folio is a location marker — it tells the reader where they are in the sequence and provides the target for every cross-reference.

**Web mechanic:** A `<div>` positioned absolutely at the page bottom. The number comes from `page_number` frontmatter. The folio is a fragment anchor target (`id="page-N"`) so cross-references can link directly to a page. The folio itself is not a link — it is the destination, not the departure point.

**Accessibility:** The folio is a `<div>` with the page number as text. It is not an interactive element. Screen readers encounter it in document flow. The page number provides a confirmation of location that is useful for all readers. The fragment anchor on the page container (not the folio itself) is the link target, so navigation lands at the top of the page, not at the page number.

**Implementation status:** Implemented (`layouts/partials/booklet/folio.html`). Currently renders only when `page_number` frontmatter is set. Not yet wired as a fragment anchor target.

---

### 6. Sequential Navigation (Previous / Next Page)

**Booklet form:** At the bottom of each page, below the folio or alongside it, a subtle affordance for advancing to the next page or returning to the previous one. In a physical booklet this is the page turn itself; on the web it is a pair of links styled to feel like turning a page rather than clicking a button. Format: "← Previous" on the left, "Next →" on the right. On the first page, only "Next" appears. On the last page, only "Previous" appears (or a "Return to Contents" link).

**Web mechanic:** Two anchor links at the bottom of each page, positioned to mirror the folio placement (previous on the left, next on the right). Links point to the adjacent pages by `page_number` order. This is plain HTML — no JavaScript required. The TOC is treated as the previous page after the cover; the cover has no previous. The TOC is also reachable via a consistent link from every page (e.g., a small "Contents" link near the folio).

The link text includes the destination page number and title for context: "← p. 2 — How to Use This Guide" / "The Three Domains — p. 3 →". This way the reader knows what they are advancing to before they turn the page.

**Accessibility:** Links are standard `<a>` elements — keyboard focusable, `Enter` to activate. Screen readers announce the full link text including destination. Focus moves to the top of the new page on navigation (standard browser behavior for same-origin navigation). A skip link at the top of each page allows jumping past the running header directly to content.

**Implementation status:** Not yet implemented. Depends on the Hugo content taxonomy (pages ordered within sections) being finalized during the runtime milestone.

### 7. Marginalia Cross-References

**Booklet form:** Handwritten-style annotations in the margin that point the reader to related content elsewhere in the handbook. Format: "↪ See page 5" or "↪ The decision process is explained on page 15." These are authored notes, not generated links — they reflect a real person's knowledge of what else in the handbook would help the reader.

Cross-references appear in the marginalia column (on `marginalia-heavy` pages) or as inline marginalia shortcodes (on any page form). The arrow (↪) is the visual signal for "this points somewhere."

**Web mechanic:** The cross-reference text contains an anchor link to the target page. The link is styled in the marginalia font and color to preserve the handwritten annotation feel. The link target is a page's fragment anchor (see Folios).

Inline marginalia cross-references use the `{{< marginalia >}}` shortcode with a Markdown link inside:

```text
{{</* marginalia */>}}
↪ The decision-making process is explained on page 15 (`../ways-of-the-work/`).
{{</* /marginalia */>}}
```

Sidebar marginalia cross-references use the `marginalia` frontmatter array with Markdown links in the text.

**Accessibility:** Marginalia is in an `<aside>` element with `aria-label="Marginal note"`. Links within marginalia are standard `<a>` elements — keyboard focusable, announced by screen readers with the link text and the fact that they are inside an aside. The `↪` arrow character is decorative; the link text is meaningful without it.

**Implementation status:** Partially implemented. The marginalia rendering pipeline (shortcode + frontmatter array) exists. Cross-reference content is author responsibility — the mechanism supports Markdown links in marginalia text, but no cross-references have been authored yet.

---

### 8. Chapter Openers

**Booklet form:** A full page that marks the start of a new chapter. Contains: "Chapter N" label, chapter title, and a one-line description of what the chapter covers. Vertically centered on the page. A chapter opener is a visual landmark — the reader knows they have crossed a boundary and entered new territory.

**Web mechanic:** A dedicated page (`page_form: chapter-opener`). The chapter opener is the first page of each chapter and serves as the link target when navigating to a chapter from the TOC. After the chapter opener, the reader continues into the chapter's content pages via sequential navigation.

**Accessibility:** The chapter number is a `<p>`, the title is an `<h1>`, the description is prose. No special interaction — the chapter opener is a content page, not a control. Screen readers announce the heading hierarchy naturally.

**Implementation status:** Implemented (`layouts/partials/booklet/chapter-opener.html`).

---

### 9. Key to Symbols

**Booklet form:** A visual glossary (page 23, in Chapter 7: Signs & Signals) that maps every stamp, marginalia convention, diagram symbol, and ornament to its meaning. A field guide always explains its symbols. This is the reference page a reader returns to when they encounter a symbol they do not recognize. Format: symbol on the left, meaning on the right — like a dictionary entry or a map legend.

**Web mechanic:** A `single-page` page form. Symbols are rendered as their corresponding CSS components (a stamp, a marginalia block, a callout box) next to their description. This is a content page, not an interactive widget. The Key is linked from "How to Use This Field Guide" (page i) and from marginalia cross-references when a symbol needs explanation.

**Accessibility:** Standard semantic HTML. Each symbol-meaning pair is a definition list (`<dl>`) or a structured description. Screen readers encounter the symbol's text and its meaning in sequence. The visual rendering of the symbol is decorative — the text content carries the meaning.

**Implementation status:** Defined in content map (page 23). Not yet implemented.

---

### 10. Endpaper

**Booklet form:** The final page (page 26). A closing stamp and a note: "This field guide is never finished. Annotate yours. Add what you learn. Pass it on." The endpaper signals closure — the reader has reached the end of the guide. No "next page" link appears here; instead, a link back to the TOC or cover is appropriate.

**Web mechanic:** A `single-page` page form. The endpaper is a content page. Sequential navigation ends here — the "Next" link is absent or replaced with "Return to Contents."

**Accessibility:** Standard semantic HTML. The endpaper is the terminal page in the sequence — screen readers will not encounter a "next page" link, signaling completion.

**Implementation status:** Defined in content map (page 26). Not yet implemented.

## Multi-Device Walkthrough

### How does an employee find the time-off policy?

An employee wants to know the organization's time-off policy. They have never opened the handbook before. Here is one credible path through the navigation model.

**Step 1 — Cover.** The employee opens the handbook. They see the cover: "Field Guide to the Organization," subtitle, "First Edition" stamp. They understand this is an authored guide, not a standard HR portal.

**Step 2 — Sequential navigation to "How to Use This Field Guide" (page i).** From the cover, the employee advances to the next page. They learn how the handbook works: what marginalia means, how page numbers work, that symbols are explained in the Key, that chapters can be read in any order.

**Step 3 — Sequential navigation to the Table of Contents (page ii).** The employee turns to the TOC. They scan the chapter list and see:

> **3 — Field Notes for the First Week** …………… 7
> _A practical, day-by-day companion for the first week._

The description suggests practical policies. The employee clicks the chapter title and navigates to page 7 (the chapter opener).

**Step 4 — Chapter opener (page 7).** The employee arrives at "Field Notes for the First Week." The running header confirms "Field Guide — First Week." The description previews what the chapter covers.

**Step 5 — Sequential navigation through the chapter.** The employee advances page by page through the chapter. On page 8 ("Setting Up Camp"), they find a section about time-off. A marginalia cross-reference points them to more detail in Chapter 6 (Field Marks & Characters, page 20) for "how the organization thinks about rest and renewal."

**Step 6 — Marginalia cross-reference.** The employee follows the marginalia link to page 20. They find the People domain's perspective on time off, including the policy details.

**Alternative path — Direct from TOC.** If the employee already knew the handbook's structure (return visit), they would go directly from the TOC to the relevant chapter without stepping through sequentially. The TOC links work as direct jumps.

**Alternative path — Cross-reference from a colleague.** A colleague says "the time-off policy is on page 8." The employee navigates to the TOC (the consistent entry point reachable from any page) and clicks page 8. Folios as reference targets make this possible.

**Why this works:**

- The employee was not dumped into a search box and asked to guess keywords.
- The TOC gave them a structural overview — they learned what else is in the handbook while finding their answer.
- Running headers confirmed their location at every step.
- The marginalia cross-reference connected related topics in a way that felt helpful, not algorithmic.
- Every navigation action was a standard link click — no JavaScript, no dynamic loading, no broken back button.

**Why this is not a website:**

- There is no sidebar. The employee did not browse a tree of nested categories.
- There is no search bar. The employee navigated by structure, not by query.
- The path is discoverable without being flat. The handbook has depth, but the depth is organized — not hidden behind faceted navigation.
- The TOC was a place the employee visited, not a widget that followed them around.

## Deliberate Exclusions

Every exclusion is a choice. Nothing is omitted by default.

### Search

**Why excluded:** A field guide does not have a search bar. Search makes the handbook a database — the reader queries it, extracts an answer, and leaves. The handbook is designed to be read, explored, and returned to. The TOC, running headers, sequential navigation, and marginalia cross-references together provide enough wayfinding that search is not required for usability.

**Risk acknowledged:** A real employee in a hurry might want to type "time off" and land on the answer. The counterargument: the handbook is not an HR knowledge base; it is an orientation experience. An employee who needs a fast factual lookup can ask a colleague or consult the actual HR system. The handbook's job is to build understanding, not to be the fastest possible answer-retrieval machine.

**Future consideration:** If the handbook grows beyond the proof-of-concept and search becomes a real user need, a static search index (e.g., Pagefind, Lunr) could be added as a dedicated "Search" page — not as a persistent search bar. A search page is consistent with the booklet model (it is a page you visit, like the TOC). A search bar on every page is not.

### Persistent sidebar navigation

**Why excluded:** The design brief explicitly rejects "exhaustive sidebar trees" (must-not-feel: documentation wiki). A persistent nav sidebar is the single strongest signal of "website, not booklet." It turns every page into a node in a tree rather than a page in a sequence.

### Breadcrumbs

**Why excluded:** Breadcrumbs (`Home > Chapter > Page`) are a web pattern for orienting within deep hierarchies. The handbook has a shallow structure (two levels: chapter → page). Running headers already provide orientation (section + chapter). Breadcrumbs would duplicate that function in a web-native visual language that contradicts the booklet aesthetic.

### Tag or category filtered listing

**Why excluded:** Tags are a content-management taxonomy, not a booklet device. A field guide's organization is an authored argument — the sequence of chapters and the placement of each topic reflect a person's judgment about what matters and in what order. Tags reduce that argument to a flat, faceted database.

### Related-links widget

**Why excluded:** Machine-generated "related pages" links are the algorithmic equivalent of authored marginalia cross-references. The handbook uses the authored version. A "Related pages" footer would duplicate the function in a way that reads as web template, not field guide.

### Back-to-top button

**Why excluded:** A floating "back to top" button is a scroll-based web pattern. The handbook is composed for pages, not long scrolls — each page is a bounded space that fits within the viewport or requires minimal scrolling. If a page grows long enough to need a back-to-top affordance, the content should be split across two pages instead.

### External link icons

**Why excluded:** Standard web practice is to mark external links with an icon (↗). The handbook's field-guide aesthetic would be broken by generic UI icons. If an external reference is important enough to include, the surrounding prose should make the destination clear. An external link in the references section reads as a citation, not as a "you are leaving this site" warning.

| --- | --- | --- | --- |
| Cover | Front door | Yes | No (static page) |
